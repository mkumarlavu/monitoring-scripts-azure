7. REVIEW CONFIGURATION
collector.json initially collects every completed source workflow as unclassified
until its numeric workflow ID has a reviewed WorkflowMappings entry, for example:
  "42": {"Service":"doc-extraction","Environment":"development",
         "IsDeploymentPipeline":false}
42 is illustrative, not an actual confirmed workflow ID.
StageMappings is keyed by the same numeric workflow ID. Use exact job names and
optional exact step names as in config/stage-mapping-example.json. Matrix job
names may include values in parentheses. Unmapped rows are still collected.
Step mappings override job mappings. No stage is inferred from a tool name.

DeploymentEnvironments must be agreed with Chinchia. An illustrative entry is:
  "development": {"Service":"doc-extraction","Environment":"development",
                  "Production":false,"SuccessMeansDeployed":true}
Set SuccessMeansDeployed true only after confirming linked GitHub deployment
success is emitted after the actual deployment completes. A build finishing
successfully is not proof of a deployment. Do not label non-production as production.

8. PREVIEW WITHOUT AZURE WRITES
Actions > NWB CI/CD collector > Run workflow.
Use a real completed application run ID, its attempt number, publish=false.
Review workflow/job/step records and source links. Verify cancelled, failed,
skipped and matrix cases. Never check out the triggering run's code in the collector.
Actions > NWB collector health > Run workflow > publish=false.
Confirm it can read collector outcomes and produces a heartbeat preview.
An empty deployment result is expected until confirmed deployment evidence exists.

9. VERIFY INGESTION
Run the collector manually with publish=true for the agreed test run.
Run the health workflow manually with publish=true.
After ingestion, query all applicable tables in Workspace > Logs:
  NWBPipelineExecution_CL | take 20
  NWBCollectorHealth_CL | take 20
Use verify-workflow.kql and verify-deployments.kql for the original tables.
Use a suitable time range; event observation timestamps are UTC.
Confirm row counts, correct run attempts, null timings and stage classifications.
Re-run the test and check the supplied queries deduplicate observations.
An accepted ingestion request alone does not prove the table rows are queryable.

10. ENABLE AUTOMATIC COLLECTION AND WATCHDOG
After successful previews and ingestion tests, set all four flags in step 6 true.
The collector observes completed workflows in THIS repository. Monitoring
workflows are excluded; skipped trigger entries may still appear in Actions.
The watchdog requests a run every 15 minutes. GitHub scheduling can be delayed;
the draft missing-heartbeat threshold is 60 minutes and must be tested locally.
Verify the first automatic run and at least two scheduled heartbeats.

11. PREPARE ALERTS
Read METRICS-AND-ALERTS.txt. Load infra/alerts-disabled.json through Azure custom
template deployment only after the tables exist. Supply workspaceResourceId.
Supply approved Action Group resource IDs and reviewed selectedWorkflowPaths
(for example .github/workflows/actual-approved-file.yml). Empty paths match none.
All three resources are disabled even if an action group is supplied.
Confirm Azure validates each query. Review threshold, severity and destination;
then enable one rule at a time in Monitor > Alerts > Alert rules.
Test heartbeat loss, a controlled collector failure, a selected workflow failure,
and recovery using approved test workflows. Check duplicates and notification load.
Azure auto-resolution means the alert condition cleared; it does not prove the
underlying pipeline was repaired. Failures age out of the one-hour observation window.
Changing queries/*.kql requires regenerating alerts-disabled.json with
infra/Build-AlertTemplate.ps1 before redeployment.

12. SERVICENOW IS A LATER INTEGRATION STEP
No ServiceNow ticket is sent by this package. Agree severity, persistence,
assignment group, deduplication key, authentication and resolution policy before
connecting an approved Action Group/integration. CI failures do not automatically
qualify as bank service incidents. Test creation, updates and recovery without
creating repeated tickets for the same issue.

ROLLBACK
Set the four automation/publish flags false and disable any enabled alert rules.
Manual runs remain available with publish=false. Do not delete historical tables.
