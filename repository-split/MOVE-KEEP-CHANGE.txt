2. Merge actions/nwb-cicd-monitoring, both reusable workflows and monitoring/ into

4. Merge the caller PR into doc_extraction's default branch.
5. Complete the preview and Azure publication checks below before enabling flags.

For later compatible monitoring changes, test and merge a PR in devops-workflows
main. Future new monitoring runs use main without editing each caller repository.
Merging central code does not itself trigger collection in application repositories.
Caller configuration changes are still needed if a change introduces required
inputs, variables or mapping fields. Maintain backwards compatibility for callers.
Use PR review and required checks on main because changes affect all onboarded repos.
Avoid a tag named main, since a same-named tag takes precedence over a branch.
The workflow and action @main references resolve separately; do not assume they
are an atomic snapshot if main changes while a run is starting. Failed-job reruns
can reuse an earlier workflow revision; use a fresh run to validate an update.

ADMIN CONFIGURATION
In devops-workflows: Settings > Actions > General > Access. Allow use by approved
repositories in the northwest organization, according to the bank's policy.
In each caller: allow the central reusable workflows and composite action plus
the approved checkout and Azure Login actions. Runner access must allow the CALLER.
No personal access token or secrets: inherit is added. GitHub supplies the source
repo token and downloads the allowed shared action. The action's scripts are read
from github.action_path, so no cross-repository git checkout credential is needed.

The caller retains contents:read, actions:read, deployments:read (collector), and
id-token:write. id-token:write enables requesting an OIDC token; Azure DCR access
still requires federation and Monitoring Metrics Publisher. The reusable workflow
cannot elevate the token permissions provided by the caller.

Azure federation must trust the CALLER's identity/environment. For the pilot, check
the existing federation with show_identity=true and publish=false. If trust also
restricts job_workflow_ref, update it to the reviewed reusable workflow reference.
For each new repo, confirm its own federation and identity permissions with admin.
Do not assume the doc_extraction federation automatically trusts another repo.

VALIDATE BEFORE REMOVING THE OLD SCRIPTS
1. Actions > NWB CI/CD collector > Run workflow on the default branch.
2. Enter a completed application run ID, run_attempt=0, publish=false.
3. Confirm the run calls the reusable workflow and loads the central action from main.
4. Confirm preview records say Repository=northwest/doc_extraction and preserve
   correct source links, stage mappings and deployment evidence.
5. Run NWB collector health with publish=false.
6. If federation needs checking, run the collector with show_identity=true and
   publish=false; only issuer, subject and audience should be printed.
7. Run controlled publish=true checks for collector and health. Verify records
   appear in Log Analytics. A completed API call alone is not sufficient evidence.
8. Confirm no other workflow references scripts/nwb-observability before removing
   that folder in a separate cleanup commit. Preserve scripts/IL.
9. Enable the four automation flags after validation. Observe an automatic
   collection and scheduled heartbeat. Monitoring job approvals can delay runs.

ROLLBACK
For a shared-code regression, revert the offending PR in devops-workflows main.
Future new runs use the reverted implementation. To roll back the initial migration,
set the four flags false and revert the caller replacement to the last working
standalone workflow/script commit. Existing Azure resources and data remain intact.

SECOND REPOSITORY ONBOARDING
Copy just the two caller YAML files referencing main and a reviewed collector.json into the
second repo. Configure its runner labels, flags, environment, variables and Azure
federation. Keep the caller workflow filenames unchanged because the health script
looks up nwb-cicd-collector.yml. Run the same preview and publish checks. Verify
Repository and Service values before enabling it.

The shared script validates the northwest organization and approved enterprise
host. Actual authorization comes from repository/action access, caller token,
runner access and Azure federation/RBAC; organization membership alone is not an
Azure authorization grant. Future non-Northwest-host support is not included.
